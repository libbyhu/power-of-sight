# 00 開發規範

本專案的命名、格式、提交與測試約定。新增程式碼前請先閱讀；規範本身的修改也以一般變更的方式提交。

## 1. 自動格式化

格式由工具決定，不手動調整。提交前執行：

| 位置 | 指令 | 工具 |
|---|---|---|
| `frontend/` | `npm run format` | Prettier（含 Tailwind class 排序） |
| `frontend/` | `npm run lint` | ESLint（`next/core-web-vitals`） |
| `backend/` | `./mvnw spotless:apply` | Spotless + Palantir Java Format |

GitHub Actions 會以 `format:check` 與 `spotless:check` 檢查，格式不符時建置失敗。

- 例外：`frontend/lib/castle/castle.js` 為逐像素定位的繪圖程式，排除於 Prettier 之外以保留原排版。
- 各編輯器的縮排與換行由根目錄的 `.editorconfig` 統一；換行一律為 LF（`.gitattributes`）。

## 2. 命名

| 對象 | 規則 | 範例 |
|---|---|---|
| Java 類別 | PascalCase，依層級加後綴 | `EntryService`、`EntryController`、`EntryRequest` |
| Java 方法、變數 | camelCase | `findOwn`、`displayOrder` |
| React 元件與檔名 | PascalCase | `MediaCard.tsx` |
| 非元件的 TS 模組 | camelCase | `client.ts`、`useApiError.ts` |
| 資料表、欄位 | snake_case，表名用複數 | `media_items.release_year` |
| JSON 欄位 | camelCase | `releaseYear`、`coverUrl` |
| 列舉值（API 與資料庫） | 大寫底線 | `IN_PROGRESS`、`MOVIE` |
| 翻譯鍵 | `命名空間.鍵`，小寫開頭 camelCase | `room.emptyFiltered` |
| Tailwind 顏色 | 只用 `tailwind.config.ts` 的語意色票 | `bg-surface`、`text-muted` |

## 3. 程式結構

**後端（三層）**
- `controller`：只處理 HTTP——解析參數、`@Valid` 驗證、決定狀態碼。不寫商業邏輯。
- `service`：商業邏輯與交易（`@Transactional`）。每個公開方法的第一個參數是 `ownerId`。
- `repository`：資料存取。查詢單筆收藏一律同時比對 `id` 與 `ownerId`。
- `entity` 不直接回傳給前端；對外一律經過 `dto`。
- 可預期的錯誤丟 `ApiException`，由 `GlobalExceptionHandler` 統一轉成錯誤格式。

**前端**
- 頁面放在 `app/[locale]/`；需要互動的部分拆成 `'use client'` 元件，頁面檔本身保持精簡。
- 所有後端呼叫經過 `lib/api/client.ts`；型別定義在 `lib/api/types.ts`，與後端 DTO 一一對應。
- 畫面上的文字一律放在 `messages/zh-TW.json` 與 `messages/en.json`，兩個檔案的鍵必須一致。
- 顏色、圓角、陰影只使用設計色票（見 [01 架構與技術選型](01-架構與技術選型.md)）；畫面元件中不寫色碼。

**註解**
- 以繁體中文撰寫，說明「為什麼」而非重述程式在做什麼。

## 4. API

- 路徑以 `/api` 開頭；目前登入者的資源放在 `/api/me/...`。
- 會員 id 只從 JWT 取得；請求內容不接受 `ownerId` 等身分欄位（未知欄位回 400）。
- 修改採整份取代（`PUT`），需要防止覆寫的資源帶 `version`。
- 清單一律分頁：`page`（0 起）、`size`（上限 100），回應格式為 `{ items, page, size, totalItems, totalPages }`。
- 錯誤格式固定為 `{ code, message, fields? }`；`code` 為大寫常數，前端依 `code` 顯示對應語言的訊息。
- 新增或修改 API 時同步更新 [03 API 規格](03-API規格.md)。

## 5. 資料庫

- 所有資料表變更都透過 Flyway：`backend/src/main/resources/db/migration/V{n}__{說明}.sql`。
- **已提交的 migration 不得修改**；修正或取消功能時新增下一個版本。
- SQL 必須同時能在 H2（PostgreSQL 相容模式）與 PostgreSQL 執行。
- 主鍵使用 UUID；時間欄位使用 `timestamp with time zone`，並有 `created_at`、`updated_at`。
- 約束（`check`、`unique`）要明確命名，以便日後移除。
- 新增或修改資料表時同步更新 [02 資料庫設計](02-資料庫設計.md)。

## 6. 測試

- 後端整合測試位於 `backend/src/test`，以 MockMvc 送出實際 HTTP 請求。
- 每個新的 API 至少涵蓋：正常流程、欄位驗證失敗、未登入（401）、存取他人資料（404）。
- 修正錯誤時先寫出能重現問題的測試，再修改程式。
- 前端以 `npm run typecheck` 與 `npm run build` 確認型別與建置。

## 7. Git

**分支**
- `main` 永遠保持可以執行。
- 新功能或修正在分支上進行，命名為 `類型/簡短說明`，例如 `feat/book-search`、`fix/login-redirect`。
- 透過 Pull Request 合併回 `main`；GitHub Actions 全部通過後才合併。

**Commit 訊息**（[Conventional Commits](https://www.conventionalcommits.org/)，英文、祈使句）

```
<類型>: <摘要>

<選填：為什麼這樣改>
```

| 類型 | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修正錯誤 |
| `docs` | 只改文件 |
| `style` | 只改格式，不影響行為 |
| `refactor` | 重構，不改變行為 |
| `test` | 新增或修改測試 |
| `chore` | 建置、工具、相依套件 |
| `ci` | GitHub Actions 設定 |

範例：`feat: add book search via Google Books`、`fix: keep filters when changing sort order`。

- 一個 commit 只做一件事；格式化與功能修改分開提交。
- 不提交 `.env`、金鑰、本機資料庫（`backend/.local-data`）與建置產物。

## 8. 安全

- 密碼只存 BCrypt 雜湊；JWT 放在 httpOnly、SameSite=Lax 的 cookie。
- 正式環境的 `JWT_SECRET`、資料庫密碼只從環境變數讀取，不寫進程式碼或設定檔。
- 錯誤回應不包含堆疊追蹤與內部訊息（`server.error.include-*=never`）。
- 使用者輸入的網址（例如封面）只接受 `http://`、`https://`。
